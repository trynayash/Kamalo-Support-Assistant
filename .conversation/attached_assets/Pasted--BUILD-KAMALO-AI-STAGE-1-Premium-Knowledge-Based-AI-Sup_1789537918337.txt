# BUILD KAMALO AI — STAGE 1

## Premium Knowledge-Based AI Support Assistant

You are building **Stage 1 of KAMALO AI**, the first foundation of a future AI Support & Resolution Engine.

IMPORTANT:

This is **NOT yet the full KAMALO AI Support & Resolution Engine**.

Do NOT implement live transaction APIs, Coin APIs, Commission APIs, FINCADO APIs, Notification APIs, financial write actions, refunds, Coin adjustments, ticket/SLA workflows, autonomous agents, multi-agent systems, or production financial reconciliation.

Stage 1 is a **standalone, production-quality KAMALO AI chatbot** that provides excellent KAMALO-specific answers using an approved KAMALO knowledge base.

The architecture MUST make it easy to connect real KAMALO engines and tools later without rebuilding the chat system.

Use the attached KAMALO AI Support & Resolution specification as the product/context source. Preserve its terminology and concepts. Do not invent KAMALO-specific business rules that are not supported by the provided knowledge.

The assistant currently has:

* NO live customer account access
* NO transaction lookup
* NO Coin balance lookup
* NO commission lookup

* NO FINCADO live progress
* NO merchant account lookup
* NO ability to change account data

unless that information genuinely exists in the Stage-1 demo data and is clearly identified as demo/test context.

When live API integration is introduced later, this restriction will be removed selectively through controlled tools.

# 10. KNOWLEDGE MANAGEMENT

Do not hardcode all knowledge directly inside one giant system prompt.

Create a knowledge model.

Example:

```ts
KnowledgeArticle {
  id: string;
  title: string;
  category: string;
  content: string;
  version: number;
  status: "draft" | "approved" | "archived";
  effectiveFrom?: Date;
  effectiveUntil?: Date;
  createdAt: Date;
  updatedAt: Date;
}
```

Only:

status = approved

content should be considered authoritative.

Design this for future versioning because KAMALO rules may change.

# 11. RAG

Implement RAG using PostgreSQL + pgvector.

Pipeline:

Approved Knowledge
→ chunking
→ embeddings
→ pgvector
→ semantic retrieval
→ relevant context
→ LLM

Do not use an external vector database unless there is a compelling reason.

Each chunk should retain metadata:

```text
article_id
category
version
status
effective_from
effective_until
```

Retrieve only approved knowledge.

Never retrieve archived/unauthorized content for normal answers.
